FINDING 1 (HIGHEST): HIGH-CAPABILITY TOOLS REACH THE FALLTHROUGH ALLOW, AND THE
STATED FALLBACK DOES NOT COVER THEM
------------------------------------------------------------------------------

Measured ALLOW at 61bbeb2:

  mcp__claude_ai_Supabase__apply_migration        production SQL
  mcp__claude_ai_Supabase__deploy_edge_function   production deploy
  mcp__claude-in-chrome__javascript_tool          executes JS in the browser
  mcp__claude-in-chrome__computer                 drives the desktop
  mcp__claude_ai_Google_Drive__create_file        writes a file outside the repo
  mcp__claude_ai_Gmail__send_message              irreversible outbound
  CronCreate                                      schedules a future agent run
  EnterWorktree / ExitWorktree                    changes the working tree

Allowing these is the DOCUMENTED posture, and the documentation is honest about
it: "not blocked here, detected at Stop by protected-file drift". For an MCP
write that lands on a repository file, that is true and the claim is sound.

THE GAP IS THAT MOST OF THESE NEVER TOUCH A REPOSITORY FILE. A migration applied
to production, an edge function deployed, an email sent, a browser driven, a cron
job scheduled -- none of them changes a byte under the worktree, so protected-file
drift at Stop sees nothing and has nothing to compare. For this class the stated
fallback is not a weaker layer, it is NO layer.

This is not an argument for default-denying them; that was tried at 520cee2 and
was an outage. It is an argument that the sentence "detected at Stop" should not
be read as covering them, and that whatever does cover them has to be somewhere
Stop is not. Naming it is the whole of this finding.

It also compounds the reviewer's separate finding that three layers delegate to
the Stop gate. Here is a fourth delegation, to a gate that structurally cannot
observe the action.

FINDING 2: TWO OVER-BLOCKS. BOTH TOOLS CAN NEITHER WRITE NOR EXECUTE.
------------------------------------------------------------------------------

Measured:

  SendUserFile  {path: 'CLAUDE.md'}              -> DENY  protected-control
  SendUserFile  {path: 'src/claudeGuard.mjs'}    -> DENY  protected-control
  SendUserFile  {path: '.claude/settings.json'}  -> DENY  protected-control
  ReportFindings (a finding whose file is src/claudeGuard.mjs)
                                                 -> DENY  protected-control

SendUserFile READS a file and shows it to the operator on another device. It
cannot modify anything. The effect is that the operator cannot be sent CLAUDE.md
or .claude/settings.json -- the two files most likely to be wanted while
debugging the guard.

ReportFindings is worse in kind: it is how a code review reports its results. A
SECURITY REVIEW OF THE GUARD ITSELF CANNOT BE REPORTED THROUGH THE NORMAL
CHANNEL, because the findings name the guard's own files. A control that blocks
the reporting of problems with that control is a specific and unfortunate shape.

Both are the path rail being unable to distinguish "about to modify CLAUDE.md"
from "referring to CLAUDE.md". The guard's own header already names this hazard
for Read -- "routing it through the write checks would refuse `Read CLAUDE.md` --
a guard that blocks reading the rules is one people turn off" -- and the fix
there was membership in READ_ONLY_TOOLS, which is consulted first. These two
tools were not given that membership. By c8's stated rule, a tool that can
neither execute nor write belongs in READ_ONLY_TOOLS and the repair is one line
each.

ONE HONEST COUNTER-ARGUMENT, because it should be decided rather than assumed.
SendUserFile sends content OUTWARD, so refusing to ship guard configuration off
the machine is a defensible policy. But nothing states that intent: the id is
`protected-control` and the reason is write-protection wording. And CLAUDE.md is
committed and pushed to a remote already, so refusing to send it buys nothing
that is not already public. If the exfiltration reading is what is wanted, it
deserves its own refusal id saying so.

FINDING 4: THE BACKSTOP HAS A DEPTH FLOOR, MEASURED AND NOW RECORDED
------------------------------------------------------------------------------

  protected path nested at depth 4  -> DENY   protected-control
  protected path nested at depth 5  -> ALLOW

This is documented behaviour (depth > 4, seen.n > 200), not a hidden defect, and
the bound exists for a good reason: an unbounded walk on every tool call is a
hook that hangs, and a hook that hangs is the silent-allow failure in a different
costume. It is recorded here so that a later reader does not assume the walk goes
all the way down. Anything that can place a path below depth 5 in an
unanticipated field is not caught by the backstop.
